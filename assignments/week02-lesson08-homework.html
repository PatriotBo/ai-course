01. 校验通过，为什么仍然可能是错误答案？

材料只说明“回滚参数后延迟恢复”，没有确认因果关系。模型补齐全部字段后输出 status=complete、confirmed_root_cause=连接池参数错误。

请区分 JSON、Schema、业务规则、任务 Eval 各能发现什么，说明 L07 的 10 个确定性单测为什么不足以证明 Prompt 效果。

展开参考答案

JSON 解析只检查语法；Schema 检查字段、类型与枚举；现有业务规则只检查已编码的条件，例如 complete 与 unknown 的矛盾。模型填了一个非 unknown 的错误根因，可能绕过这些检查。

任务 Eval 应对照材料判断证据支持度：回滚与恢复相关不等于根因已确认，因此应失败或交人工复核。L07 单测使用固定输出测试程序行为，没有覆盖真实模型在多类输入上的表现。程序单测通过与模型任务质量必须分别报告。

判分要点：不能把 Pydantic 当事实验证器；不能只回答“模型有幻觉”而不解释哪层遗漏。

02. Prompt 改版的实验清单缺了什么？

某同事只记录：

{"prompt_version": "v2", "model": "latest", "score": 0.92}

至少补充 8 项，使其能够追溯和公平比较，并解释为什么不能把 API key 也写入清单。

展开参考答案

至少包括：prompt_key、不可变模板内容或版本引用、baseline 版本、dataset version、evaluator/rubric version、schema version、实际 Provider 和 base_url、模型请求别名与可获得的实际模型标识、生成参数、repair policy、runner revision、实验 run_id、每 case 重复次数、并发、缓存策略、价格快照和原始输出的受控引用。

“latest”可能变化；若拿不到模型快照 ID，应标注不可获得、记录时间和已返回的标识，不伪造确定性。API key 是调用凭据，不是评估证据；只从安全配置读取，不放日志、Git 或公开报告。

03. 同时改 Prompt 与模型，能否归因？

v1 使用模型 A，v2 使用模型 B 且多加两个 few-shot 示例。通过率从 80% 到 90%。能否说“两个示例使准确率提高 10%”？怎样改实验？

展开参考答案

不能：模型与 Prompt 同时变化，存在混杂因素；80%→90% 是提高 10 个百分点，相对提高 12.5%。现有证据只能说明这两个配置组合在当前测试中不同。

如果要隔离 Prompt 效果，在同一模型、同一数据/评分/参数/repair 条件下比较示例有无。必要时做模型 A/B × Prompt v1/v2 的四组实验，分别看模型效应、Prompt 效应及交互，不把所有变化归为 Prompt。

04. 设计一个高价值测试 Case

设计一条“付款后订单仍显示未支付”的 case。要求包含 case_id、group_id、input、expected 和 tags；明确哪些数据发给模型、哪些只给评分器。

展开参考答案
{
  "case_id": "PAY-001",
  "group_id": "payment-incident-001",
  "input": {
    "feedback": "用户说已付款两小时，但订单页仍显示未支付。没有支付网关查询结果。"
  },
  "expected": {
    "must_distinguish": "用户陈述与可信系统状态",
    "required_action": "查询订单和支付记录",
    "forbidden_claim": "已确认支付成功或失败"
  },
  "tags": ["payment_state_unknown", "user_claim_not_system_fact"]
}

Prompt 只接收 input 与稳定任务规则。expected 给 evaluator，用来判断输出是否违反证据边界；group_id 用于去重和划分同源样本。若整条 case 都送模型，相当于把评分答案塞进试题。

此题没有唯一正确文案，但必须避免把用户陈述视为数据库事实。

05. 同一事故 20 个改写，随机拆分合理吗？

把同一个事故描述改写 20 次，然后随机把 16 条放开发集、4 条放留出集。这样得到的验收结果可靠吗？

展开参考答案

存在同源泄漏。虽然字符串不同，关键事实、难点和答案都高度相似，留出样本并不真正独立。

先按原始事故/文档来源 group_id 去重与分组划分，再在各自集合内部扩增；近重复、同一用户任务、多轮上下文也需要整体划分。评估统计时不把这 20 个改写等同 20 条独立事故。扩增可以丰富表达，不自动扩大业务覆盖。

06. 标签写错了怎么办？

发现留出集一条“未确认根因”的样本被标为 complete。能否直接改成 insufficient_context，让候选通过，然后沿用旧报告里的基线分数？

展开参考答案

可以纠正标签，但必须保留依据、评审人/角色和变更记录，生成新 dataset version，并在相同新标准下重跑或重新评分基线与候选。

不能只修候选一方。被反复查看、用来调 Prompt 的留出样本会逐步成为开发数据，需要补新的未见验收样本。不能为了让候选通过而事后改变正确性定义。

07. 哪些规则该硬编码，哪些交给 Judge？

分类并说明理由：

  • 返回字段只能有固定 8 个；
  • 摘要是否遗漏“用户影响范围”；
  • 请求是否有权限执行退款；
  • 根因断言是否被材料支持；
  • 输出是否超过 200 字。
展开参考答案
检查首选方式理由
固定字段Schema / 确定性代码边界明确、可重复
语义覆盖required facts + 校准的 Judge/人审可能有多种正确措辞
退款权限可信鉴权与业务系统不能让模型裁决授权
事实支持证据 rubric + Judge，关键争议人审需要语义对照，不只是字符串匹配
字数确定性计数先定义按字符、词还是字节计数

可计算的规则不必浪费一次模型调用；难以精确匹配的语义不要用“包含某关键词”假装完整解决。

08. 给 LLM Judge 写一个可操作量规

请为“根因是否有证据”设计 0/1/2 三档评分，规定如何输出证据，以及遇到歧义怎么办。

展开参考答案
0：明确断言某根因已确认，但输入只给相关性或猜测。
1：根因表述含糊、归属不清，无法确定是否仍保留不确定性。
2：有明确证据时准确归纳；没有证据时明确 unknown/待确认。

输出：score、evidence_quote、brief_reason、needs_review。
证据摘录必须来自输入或待评输出，不新造证据。
歧义：needs_review=true，进入人工复核，不自动当满分。

应要求简短可核验的理由，不要求内部逐步思维过程。对 judge 返回也做 Schema 校验；采样与人类标注对齐，并记录 judge model/rubric 版本。高风险关键错误不能靠流畅度加分抵消。

09. 成对实验与发布判断

100 条相同样本，无 API/judge 缺失，结果如下：两版都通过 82 条；仅基线通过 4 条；仅候选通过 10 条；两版都失败 4 条。

计算：两版通过率、提升百分点、相对增幅、新增退化率。如果 4 条退化中有 1 条违反事先规定的关键事实门禁，应怎样决策？

展开参考答案
基线通过：(82 + 4) / 100 = 86%
候选通过：(82 + 10) / 100 = 92%
净提升：92% - 86% = 6 个百分点
相对增幅：6 / 86 ≈ 6.98%
新增退化率（全部 case 为分母）：4 / 100 = 4%
原本正确样本中的退化率：4 / 86 ≈ 4.65%

4/100 和 4/86 都可使用，但必须写清名称和分母。关键事实门禁失败应阻断发布，先定位退化，再复跑相关切片与全量回归。不要忽略失败案例，也不能凭单次 100 条实验声称提升已经统计显著。

10. API 失败与 Judge 失败如何计分？

100 次生成请求：10 次 API 失败；90 次有响应，其中 81 次任务合格。先计算两种通过率。

再讨论另一场实验：生成都成功，但 Judge 有 5 次超时。能否把超时的 5 条扔掉后报告“完整测试通过”？

展开参考答案
成功响应内的合格率：81 / 90 = 90%
端到端任务通过率：81 / 100 = 81%
生成 API 错误率：10 / 100 = 10%

Judge 超时属于 evaluation_error，不代表模型回答错误，也不代表正确。应报告评分覆盖率 95/100，按事先约定补跑评分或阻断实验结论；不能无声删样本，也不能说“完整测试通过”。补跑应保留记录，不重复生成更有利的答案来替换待评分输出。

11. 计算真实的每成功任务成本

一次 100 个任务的实验，首轮生成共 ¥2.00，repair 共 ¥0.40，judge 共 ¥0.60；最终成功 80 个任务。

分别计算生成侧每任务成本、生成侧每成功任务成本和含 judge 的实验每任务成本。API 返回 usage 缺失时应填 0 吗？

展开参考答案
生成侧总成本：2.00 + 0.40 = ¥2.40
生成侧每任务成本：2.40 / 100 = ¥0.024
生成侧每成功任务成本：2.40 / 80 = ¥0.030
含 judge 的实验总成本：2.00 + 0.40 + 0.60 = ¥3.00
含 judge 的实验每任务成本：3.00 / 100 = ¥0.030
含 judge 的实验每成功任务成本：3.00 / 80 = ¥0.0375

两个 ¥0.030 恰好数值相同，但分母和用途不同。usage 缺失应标 unknown/null 并说明覆盖率，不能冒充零成本。真实生产不一定逐请求运行 judge，因此实验费用也不能直接当线上推理费用。

12. 低成本、高分候选也要拒绝吗？

候选更便宜、整体通过率更高，却在“缺信息”切片从 90% 降至 60%。正常样本占总体的 90%。你如何解释？

展开参考答案

整体指标被多数正常样本主导，掩盖关键切片退化。先对照事先设定的各切片最低要求，检查分布、样本量与标注，不能用总体平均冲掉高风险缺失信息场景。

如果“缺信息时不编造”是关键要求，候选应阻断；即便没有预设关键门槛，也不能仅凭总体均值就放量，应追加针对性评估、审查收益代价并更新后续治理规则。改变规则后应透明记录，不挑一个能让当前候选获胜的口径。

13. 代码阅读：通过标志代表什么？

阅读讲义第 7 节 score_case()。回答：为什么分别保存 raw_json_ok、contract_ok、rule_ok？rules_passed=true 能否替代完整任务评估？extra="forbid" 是否自动启用严格类型？

展开参考答案

原始输出可能夹 Markdown fence：完整 raw 不是 JSON，但 L07 提取器可以取出对象并通过契约校验。三个标志区分原始格式、容错后的契约、样本特定规则；合在一个通过分里会隐藏缺陷。

rules_passed 只表示片段实现的条件通过，没有验证 required facts 全部覆盖和全部语义证据，不应叫完整任务质量。extra forbid 只控制额外字段，不等于 strict=True；Pydantic 默认可能做类型转换。如果不允许字符串数字，应额外检查或开启 strict mode 并重新验证。

14. 给评分器列反例测试

为 score_case() 列至少 6 个测试，包括一个“看似合法但任务错误”的例子。不要调用真实模型。

展开参考答案
输入预期
全字段正确，status 与根因未知要求一致三个标志均真，rules_passed 真
同一结果外包 Markdown fenceraw_json_ok 假，contract_ok 可真，rules_passed 假
缺 impact 必填字段contract_ok 假，rules_passed 假
Schema 合法但 status 与 expected 不符contract_ok 可真，rule_ok 假
status 仍不足，但根因被填成确定推测对 must_be_unknown 样本，rule_ok 假
文本 not json 或空字符串返回不通过，不产生无解释的程序崩溃
原始输出为数组 []不是目标对象，raw_json_ok 假
原始对象包含 NaN / Infinity 常量非标准 JSON，raw_json_ok 假，不能因 Python 默认支持而算通过
测试数据 expected 本身缺字段数据集预检失败，不能计为模型答错

另外还应给统计器测试重复 case ID、空集、缺失 trial、分母、同一响应重用和价格缺失。评分逻辑错了，整个发布证据就不可靠。

15. 三次重复与缓存

40 个 case，每个版本各跑 3 次。为了省钱，后两次直接复用首次缓存。能否报告“120 个独立样本零失败，因此稳定可靠”？若 100 个真正独立二项样本零失败，又能说明什么？

展开参考答案

不能。缓存是在重复评分相同输出，不是重复生成，不能测模型随机性；40 个 case 的三次结果也不能当 120 个独立业务案例。

应明确区分 generation run 与 re-score run；测稳定性时独立生成，记录 cache policy，并按 case/group 分析重复结果。对于 100 个符合独立同分布假设的二项样本零失败，95% 单侧错误率上界的经验近似约 3/100=3%，不是未来错误率为零。相关样本不能生搬这一近似。

16. 设计一个最小发布门禁

你的事故摘要服务准备发布 v2。写出至少 6 条可执行条件，并说明为什么不能只设“加权总分超过 0.9”。

展开参考答案

可以采用以下结构，具体阈值由团队在跑实验前确定：

  1. 固定 manifest 与 dataset/evaluator 版本，要求必需 trial 齐全。
  2. 不存在未解决的 evaluation_error，或按明示规则补全后再决策。
  3. 关键证据捏造、未授权执行等阻断项为零新增，并满足绝对安全要求。
  4. 原始格式、Schema 与最终任务通过率分别达到绝对最低线及基线比较要求。
  5. 缺失、冲突、对抗等关键切片不低于预设门槛。
  6. 延迟、生成及 repair 成本符合预算，计费缺失覆盖率符合要求。
  7. 所有新增退化案例已审查，候选与旧配置具备回滚兼容性。

加权总分可能让文风优势抵消关键事实错误；必须保留独立的阻断条件，而非把所有事情都平均化。

17. 回滚时只改 production 标签够吗？

v2 Prompt 配合 Schema v2 上线后出问题。你把 production 指针改回 Prompt v1，却保留 Schema v2；正在执行的多步任务也立刻读取新指针。指出两个风险并给出方案。

展开参考答案

风险一：旧 Prompt 可能不提供 Schema v2 所需字段，回滚反而造成结构失败；需验证兼容性，必要时回滚完整 Prompt/Schema/模型/业务配置组合，不能只换字符串。

风险二：同一个进行中的任务混用版本，状态和规则可能不一致；应在请求/任务开始时固定解析版本，并记录配置快照。在途任务按明确策略完成、取消或迁移，新任务再采用回滚版本。

还应保存发布记录、触发条件、实验 ID 和影响范围，不把“切换成功”等同业务已恢复。

18. 一分钟面试回答与反追问

题目：“你如何让 Prompt 的版本迭代可测试、可上线、可回滚？”回答后再说明：离线 Eval 与线上 A/B 的区别。

展开参考答案

我用不可变的 Prompt 版本管理任务规则，把模型、Schema、数据集、评分器和 repair policy 绑定成实验清单。测试集覆盖正常、缺失、矛盾与对抗案例，划分开发、回归与留出数据，禁止把 expected 送入模型。评分先用确定性契约与硬性安全检查，再用经人工校准的 LLM judge 做有证据的语义评分。比较时对同一 case 成对评估，关注新增退化、切片、首轮及 repair 后成功率、成本和尾延迟。关键错误不能被平均分抵消。通过离线门禁后灰度，稳定分配用户或任务、监控线上业务效果，并保留与 Schema、模型兼容的回滚配置。

离线 Eval 在固定样本与规则下控制变量、复现比较；线上 A/B 在真实流量中随机分配版本，验证真实业务收益与影响。离线更好不保证线上更好；A/B 也不能省略发布前的安全校验。

判分要点：必须覆盖版本、数据、评分、比较、门禁、回滚，不要只列工具名字。

自测与提交方式

  • [ ] 我能说清实验清单为什么不止 Prompt 版本。
  • [ ] 我能独立设计防泄漏、带期望行为的 case。
  • [ ] 我能解释 judge 的偏差和校准方式。
  • [ ] 我能计算通过率、百分点、相对提升与每成功任务成本。
